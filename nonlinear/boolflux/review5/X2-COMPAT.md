## Why the unchanged file loses its goal jobs on this hub

1. **Fresh-first runs before `choose_op`.** The base `launch` now first asks `fresh_target` (a front tuple
   without its first polish / pull gets it at once) and only then calls `choose_op` / `choose_target`. As long
   as such tuples exist the goal layer's pick is never asked for. (In the smoke run every tuple was fresh:
   the archive copy came without its job history. With the history the effect lasts until every front tuple
   has had one polish and one pull.)
2. **The wrapper swap has no effect.** The base reads `self.scripts[op]` (operators registered through
   `control.json` are per scheduler since review 5), not `S.SCRIPTS[op]`. `op_goal.py` is never started, so
   `X2_CAPS` / `X2_OBJECTIVE` never reach an operator: a goal job that did get through would run without
   its goal caps.
3. `ops = [o for o in self.gops[gname] if o in S.SCRIPTS]` does not see operators registered through
   `control.json` `"scripts"`.
4. `op_goal.py` passes `--caps` and its value as two arguments; a value starting with `-` (no A cap) is
   read by argparse as an option and the operator exits 2. Not reached by the current goal list.
5. `_fix_gjoin_parents` rewrites the record file after admission. The base now records the join parents of
   every operator whose `record.json` lists `joins` per candidate, so it is redundant, and it leaves
   `archive/index.jsonl` (the readers' cache) behind the record file if the two ever differ.

## What I changed in the base class for the subclass (in the commit to merge)

- `Scheduler.tkey(i)` is now `target_key(i)` (X2's `tkey(op, i, gname)` had replaced the base method).
- Options a subclass namespace lacks or answers with `None` (`_Args`) get the base defaults; without this
  the 02:36 file stopped at start with `ValueError: gain_mode None`.
- `launch(cpu, busy)` keeps its signature; `busy` holds target ids and tuples.
- New **`Scheduler.start_job(cpu, op, why, tid, extra=(), env=None)`**: everything after the choice of
  (operator, target): unique run id with the campaign uid, fresh job directory, seconds cut to the end of the
  campaign, own process group and kill limit, script path and hash, join mark, attempts per tuple. `extra`
  is appended to the operator's command line.
- `control.json` `"cpus"` read by X2's early `self.control()` is applied after the CPU set-up.

## The patch (`review5/x2-compat.patch`, 86 diff lines, against md5 07960129)

- `launch`: the generic share is `super().launch(cpu, busy)`; a goal job is
  `self.start_job(cpu, op, why, tid, extra=['--objective', 'a,ad,cost,gd', '--caps=A,AD,GD'],
  env=dict(os.environ, X2_GOAL=gname))`. No SCRIPTS swap, no wrapper, no change of `os.environ`. `est` is
  the job's real `secs`. Fixes 1, 2, 4.
- `choose_goal_op`: `o in self.scripts`. Fixes 3.
- `finish`: the `_fix_gjoin_parents` call removed. Fixes 5.

`op_goal.py`, the `choose_op` / `choose_target` overrides and `_goal_pick` are then unused (left in place).
The patch is generated by `x2compat/make_patched.py` from X2's file; if X2 edits the file again, copy the
new version over `x2compat/scheduler_goal.py` and rerun the script (it stops with an assertion if one of
the three places has changed).

    cd ~/xcr-boolflux && git apply --check nonlinear/boolflux/review5/x2-compat.patch   # after the merge

For X2 to decide, not in the patch: goal jobs keep their own tuple caps (`TUPLE_CAP`, reset when the front
changes) next to the base caps of the generic share (`--tuple-caps`, `--cap-renew`). With the patch a goal
job also counts in the base attempts of its tuple, so the generic share and its fresh-first rule see it.
